## 1. Web App Architecture
The Cast Recruiter web app is a **Visual Card Grid Builder** deployed via `clasp` to Google Apps Script. 

### Key Features:
* **Unique ID Support:** Extracts the `ID (str)` column for characters, loyals, talismans, and specials from the backend sheet, serving them to the client as `uniqueId` properties.
* **Dual-Format Export:** The export handler in `CastRecruiter.html` outputs a highly structured JSON:
  * `championId`: String
  * `unitIdsRecruited`: Dictionary `{ uniqueId: qty }`
  * `talismanIdsEquipped`: Dictionary `{ talismanUniqueId: "Attached to: familiarUniqueId" }`
  * `specialIds`: Array of unique ID strings
  * **Backward Compatibility:** Retained all legacy keys (`champion`, `unitsRecruited`, `talismansEquipped`, `specialActions`) so older parsers still work seamlessly.

## 2. Tabletop Simulator (TTS) Importer
The TTS Importer has been fully upgraded to handle secure, foolproof unique ID-based loading and completely bypasses layout zone physics bugs.

### Upgraded Script Architecture (`tts/TTS_Loader.lua`)
* **Metadata Injection (The Scraper Fix):** 
  * The Python script (`dextrous/generate_card_images.py`) parses the CSV data files (`M3_TTS_DB - IN Cha-Tal.csv` and `M3_TTS_DB - IN SP.csv`) and automatically injects:
    1. Human-readable Name -> Injected into the visible `"Nickname"` field.
    2. Unique ID -> Injected into the invisible `"GMNotes"` field.
  * This allows players to hover over cards in TTS to see their actual names while scripting can securely identify them by ID!
* **Robust ID-Based Lookups:** 
  * `cloneCardFromDeck` checks if the deck metadata's `gm_notes` matches the unique IDs in the pasted JSON.
* **Instant Teleportation Return Physics:** 
  * When cloning, the script briefly pulls the original card out of the deck, clones it, and then puts the original card back.
  * To prevent the original card from colliding with table elements and failing to return, the script *instantly teleports* the card back onto the deck (`cardObj.setPosition(deck.getPosition())`) right before `deck.putObject(cardObj)`. This guarantees 100% absorption and zero duplicates on the table.
* **Unified Hand Dealing (The Layout Zone Fix):**
  * Spawning cards directly onto layout zones often failed because the physics engine merged them into a deck before the zone could align them.
  * The Champion, exactly **1 reference card** per recruited Familiar/Minion, Talismans, and Special Actions are all dealt directly into the player's hand.
  * This is clean, fast, and gives players absolute control to layout their cards manually without layout-zone interference.
* **Unity Reference Safety:**
  * To resolve `NullReferenceException` errors ("Object reference not set to an instance of an object"), the script re-queries the trigger zones to find the active deck references fresh on every single loop iteration.

## 3. Workflow for Content Updates
When adding new cards or modifying sheets:
1. Export the latest Saved Object JSONs from Dextrous to the `dextrous/` folder.
2. Run `python dextrous/generate_card_images.py`. This will:
   * Scan your sheets/CSVs.
   * Inject Names into Nicknames and Unique IDs into GM Notes for the TTS Saved Object JSONs.
   * Regenerate `CardImages.gs` with image sprite coordinates.
3. Use `clasp push` to sync your GAS backend.
4. Import the newly saved JSON Saved Objects in Tabletop Simulator. All cards will be fully searchable, layout-safe, and ready for deployment!

## 4. End Game UI & Webhook Submission
We have implemented a decoupled, 3D button-based End Game Controller to record match results and balance statistics, keeping the Cast Loader and End Game functions modular.

### Architecture & Components:
* **Cast Loader API (`tts/TTS_Loader.lua`)**:
  * Captures successfully loaded player casts globally (`loadedCasts`).
  * Maintains a chronological log of Special Actions (`specialActionsLog`) via a global function `logSpecialAction(playerColour, cardName, cardId)`.
  * Exposes this match data securely via a global API function `getMatchDataJson()`, which returns a serialised JSON string. This completely bypasses Tabletop Simulator's cross-script table ownership limitations ("Attempt to perform operations with resources owned by different scripts").
* **Dedicated End Game Controller (`tts/End_Game_Controller.lua`)**:
  * Attached to a separate, dedicated table token (e.g. your red/yellow brand tile).
  * Features flat, large, highly visible, color-coded 3D buttons stacked vertically in a single column (1x4) scaled to fit and drawn slightly above the surface (`y = 0.2`):
    * **Red Won** (Red background)
    * **Blue Won** (Blue background)
    * **Draw** (Grey background)
    * **Submit Game** (Green background)
  * Restricts winning declarations and submission access to the Host.
  * Dynamically highlights the selected winner using button label and color states.
  * Queries the Cast Loader via Tabletop Simulator's `call` API to retrieve match data as a JSON string, then decodes it locally so the tables are owned by the controller's sandbox.
  * Compiles, serialises, and POSTs the match record to the configured Google Web App webhook via `WebRequest.custom()`.
* **Webhook Receiver & Sheets Integration (`webapp/main.gs`)**:
  * The `doPost(e)` function in the Apps Script backend has been upgraded into an ultra-resilient parser.
  * It logs match records live to a spreadsheet tab named **`IN TTS`** (creating it on the fly if it is missing) using sequential appending via `sheet.appendRow()`.

## 5. June 2026 Importer & UI Upgrades

### Task 1: Auto-Summon Minions
* **Objective:** Automatically draw core mid-game minion cards for certain dominions.
* **Implementation:** 
  * Added a check inside the main loading coroutine of `TTS_Loader.lua`.
  * If the loaded cast belongs to **Iro-Si-Khar**, the loader instantly draws a **Driplet** card from the Characters deck and deals it to the player's hand.
  * If the loaded cast belongs to **Ahéserec**, the loader instantly draws a **Huskling** card and deals it to the player's hand.
  * Bypasses the cast recruiter and game stats upload entirely, keeping the stats and selections clean.

### Task 2: 3D Model ID Injector (Utility Script)
* **Objective:** Establish a foolproof standalone utility to prepare 3D models with database IDs.
* **Implementation:**
  * Created `tts/Model_ID_Injector.lua`. This token script can be placed on the table next to a Characters Deck (which has IDs in GM Notes) and a bag of raw models.
  * When clicked, the script matches each model in the bag against its card counterpart by Nickname, copies the card's Unique ID from its `GM_Notes` property, and assigns it to the model's `GM_Notes` before returning it to the bag.
  * The user can then right-click and save the Bag as a permanent, pre-loaded game component.

### Task 3: Model Spawning from Bags
* **Objective:** Spawn recruited 3D models directly on the table, matching the exact counts from the JSON.
* **Implementation:**
  * Introduced `MODELS_ZONE_GUID` at the top of `TTS_Loader.lua`.
  * During the load coroutine, if the Models Bag is present in this trigger zone, it iterates over `unitIdsRecruited` and extracts the models matching the Database ID (`GM_Notes`) directly.
  * Clones the model `N` times (representing the quantity recruited) and drops them onto the physical table in the player's layout zone (`config.character_zone_guid`).
  * **Dynamic Row Layout:** Arranges distinct unit types on their own rows along the Z axis, while placing duplicate models of that same type in a clean horizontal row along the X axis (shifting to the right) to prevent physical overlaps and collisions.

### Task 4: Importer Cleanup & Standardisation
* **Objective:** Streamline the importer pad to remove meandering legacy fallback code.
* **Implementation:**
  * Completely removed name-based fallback loop blocks for Units, Talismans, and Specials.
  * Enforced strict, secure unique ID-based loading as the codebase standard.

### Task 5: Native TTS Onboarding Feature
* **Objective:** Give players the ability to instantly launch learning scenarios directly in TTS without copying JSON.
* **Implementation:**
  * Integrated a native XML UI into the loader token, accompanied by a purple "Onboarding Menu" button flat on the loader pad.
  * Clicking "Onboarding Menu" toggles a clean screen-space setup panel.
  * Players choose their Champion (Flint, Ripple, Lark), select Onboarding Scenarios 1 to 4, choose their Seat (Red, Blue), and click "Load Scenario".
  * The script serialises the hardcoded scenario list into JSON and channels it directly into the robust loading pipeline, spawning the champion card, the units, their corresponding models, and any auto-summoned minions automatically.

### Task 6: Web App Signature Actions Segregation
* **Objective:** Separate Signature Actions from other generic Specials in the web app UI.
* **Implementation:**
  * Upgraded `webapp/CastRecruiter.html`'s Specials grid structure.
  * Split the DOM layout into `#signature-container` (`<h3>Signature Actions</h3>`) and `#specials-container` (`<h3>Special Actions</h3>`).
  * Enhanced `renderSpecials()` to filter cards based on their `isSignature` property, rendering them into their respective distinct grids.
  * Seamlessly handles active limits (maximum of 6 specials) and preserves the export schema cleanly.
